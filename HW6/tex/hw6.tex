    \item \textbf{Coalesced memory references}:\\
          This is a read and run-code problem. You'll get to write code in the subsequent
          problems.
          \par
          Download the source files \{hw6,hw6\_lib, hw6\_mem\}.\{cu,h\} and Makefile. Build the
          mem program:\\
          \rule{1.5em}{0ex}\texttt{make mem}\\
          Please do this on one of the linXX machines (i.e. lin01, lin02, ..., or lin25).
          \par
          If you run\\
          \rule{1.5em}{0ex}\texttt{mem}\\
          it will run a kernel with parameters where all memory references are coalesced.
          OTOH,\\
          \rule{1.5em}{0ex}\texttt{./mem - - - false}\\
          it will the kernel where all memory references are non-coalesced. See the
          comments at the beginning of hw6.cu for the many options you can use.

          \begin{enumerate}
              \item Explain why the kernel with 'coalesced' set to 'true' has all of its
                    memory references coalesced. This requires reading the code. I'll explain
                    a few key points below.

                    \begin{answer}
                        When the kernel is set with the 'coalesced' option, threads are accessing sequential data values in v spaced
                        apart by a stride equal to n\_threads.
                        \\ \\
                        Based on the gmem\_fetch function, each thread in a warp is accessing its local element in the stride
                        (stride size = n\_threads). It then adds the stride (m += my\_stride;) and adds to the accumulator.
                        \\ \\
                        The memory controller performs an optimization here. It recognizes that all of threads in a single warp
                        are asking for contiguous data elements (32 contiguous elements, a chunk). This allows the GPU to
                        make 1 request to main memory to get all required data elements for that warps stride (32 threads in the warp).
                        \\ \\
                        So all of the threads are working in a lock-step fashion. 1 global access for a chunk, then all of the threads
                        access that chunk, walk forward a stride and repeat.
                    \end{answer}

              \item Explain why the kernel with 'coalesced' set to 'false' has nearly all
                    of its memory references not coalesced. Again, read the code and my notes
                    below.

                    \begin{answer}
                        When the kernel is set without the 'coalesced' option, each thread has a random stride length.
                        This means threads in the warp are all striding at different lengths. So now at each 'stride' within the
                        warp it is requesting 32 non coalesced global memory accesses. So this results in 32 separate accesses.
                    \end{answer}

              \item Why do we get more accurate estimates when n (the number of int's in
                    the main data array) is large? Feel free to experiment with different
                    values for n. I recommend using power-of-two values. It is sufficient
                    to make the observation and explain the trends in terms of the architecture
                    features.
                    \par
                    Hint: if you want to dive deeper into this problem, you can use these
                    measurements to estimate the L2 cache size and miss penalty.

                    \begin{answer}
                        We get better estimates for the reduction of global memory accesses with coalesced patterns
                        when the input array is large because we have L2 cache evictions. When the input array is small enough
                        it can actually fit completely within the L2 cache, at this point we are just measuring cache speed.
                        So even if threads within a warp have non-coalescing memory accesses, the negative effects may be mitigated
                        by the data they need being in the cache already. So this doesnt accurately illustrate the improvement of
                        coalesced memory accesses (as it reduces global mem accesses in general).
                        \\ \\
                        \begin{center}
                            \begin{tabular}{|l|c|c|c|}
                                \hline
                                N                    & Coalesced (ms) & Uncoalesced (ms) & Speedup \\
                                \hline
                                $2^{18}$ (262,144)   & 3.5102         & 82.0949          & 23.4x   \\
                                $2^{22}$ (4,194,304) & 12.0334        & 518.5196         & 43.1x   \\
                                $2^{26}$ (Default)   & 25.2642        & 720.5259         & 28.5x   \\
                                \hline
                            \end{tabular}
                        \end{center}
                    \end{answer}

              \item What is the memory bandwidth achieved when the memory references are
                    coalesced?

                    \begin{answer}
                        With $n\_threads = 73,728$ and $n\_read = 50,000$, the total data read is $73,728 \times 50,000 \times 4 \textrm{ bytes} \approx 14.75 \textrm{ GB}$.
                        With a time of $25.15$ ms, the bandwidth is:
                        $$ \frac{14.7456 \times 10^9 \textrm{ bytes}}{0.0251517 \textrm{ s}} \approx 586.3 \textrm{ GB/s} $$
                    \end{answer}

              \item What is the memory bandwidth achieved when the memory references are

                    \end{answer}

              \item How much longer does it take a warp to do WarpSize global memory

                    \begin{answer}

                        \\
                        It takes approximately $28.6$ times longer.
                        \\ \\
                        This seems correct as the WarpSize is 32 threads. In the worst case each warp will have to make 32 different global memory accesses
                        in a stride.
                    \end{answer}

          \end{enumerate}

          Notes about collisions:
          \par
          The \code{gmem\_fetch} kernel has each thread perform \code{n\_read} reads from the
          global memory. Let\\
          \rule{1.5em}{0ex}\code{i = blockDim.x * blockIdx.x + threadIdx.x}\\
          be the global index of the thread. Thread i first reads from array
          index \code{i}, then \code{(i+stride[i]) \% n}, then \code{(i+2*stride[i]) \% n}, and so on.
          \par
          The $k^{th}$ read (with $k$ starting at $0$) is from\\
          \rule{1.5em}{0ex}\code{ar[i + k*stride[i]]}.\\
          To get all of the accesses coalesced, the stride array is initialized
          so that \code{stride[i]=gridDim.x*blockDim.x} (i.e. the total number of threads).
          \par
          Why does this produce coalesced memory accesses? (i.e. Q1.a).
          \par
          To get the accesses non-coalesced (with high probability), \code{stride[i]}
          is initialized to a random integer with \code{0 <= stride[i] < n}. Why does
          this produce non-coalesced reads (with high probability)?
          \par
          We would get even better randomization if for each read, each thread
          independently chose a new random address in $0...n-1$. But, pseudo random
          number generation is much slower than a single global memory access;
          so this would make measurements difficult. The method I used is,
          empirically, just as good and keeps the kernel memory bound.

    \item \textbf{Shared memory collisions}:\\
          In this problem, you will write a new kernel, similar to the \code{gmem\_fetch} kernel in \texttt{hw6\_lib.cu}. Call this kernel \code{smem\_collide}. With this kernel each block should perform a collaborative read to load data from global memory into shared memory. Each thread should then perform a large number of reads from the shared memory. These reads should use indexing methods similar to those in \code{gmem\_fetch} so the compiler can't figure out the access pattern at compile time (it should depend on the parameters used when running the program).
          \begin{enumerate}
              \item Find an access pattern so that if \code{n\_read} is large enough, every thread in the block will eventually read from every location loaded into the shared memory and these reads incur no shared memory collisions. Describe what property an access pattern needs to have to ensure that there are no shared-memory collision. Explain why your access pattern satisfies this property. Your description and explanation should be similar in level of detail to the explanatory note for Q1.

                    \begin{answer}
                        To ensure no shared memory collisions, we use a constant stride of 1. This means setting \code{stride[i] = 1} for all thread.
                        Each thread $t$ starts accessing the shared memory at index $m = t$ (where $t$ is \code{threadIdx.x}). At each step $k$, the thread accesses index $m_k = t + k \times 1$.
                        Shared memory banks are determined by $Address \pmod{32}$.
                        For a warp of 32 threads ($t \in \{0, \dots, 31\}$), at any step $k$, the bank accessed by thread $t$ is:
                         $$ \textrm{Bank}_t = (t + k) \pmod{32} $$
                        Since $t$ ranges from $0$ to $31$, the values of $(t+k) \pmod{32}$ are simply a cyclic shift of the values $0 \dots 31$. They are all distinct.
                        Because every thread in the warp accesses a unique bank simultaneously, there are zero bank conflicts, maximizing parallelism.
                    \end{answer}

              \item Find an access pattern so that if \code{n\_read} is large enough, every thread in the block will eventually read from every location loaded into the shared memory and these reads incur the maximum shared-memory collision penalty. I.e. you are trying to make the code as *slow* as possible. Describe what property an access pattern needs to have to maximize the shared-memory collision penalty. Explain why your access pattern satisfies this property. Your description and explanation should be similar in level of detail to the explanatory note for Q1.

                    \begin{answer}
                        To maximize shared memory collisions, we use random strides. We initialize the stride array with random values using \code{ai\_rand}.
                        This assigns a random stride $S_i$ to each thread.
                        Unlike the constant stride case where the relative spacing ($Addr_a - Addr_b$) is preserved, random strides cause the threads to jump to arbitrary offsets relative to each other.
                        At any given step, the 32 threads in a warp access 32 effectively random addresses. By the birthday paradox, mapping 32 items randomly into 32 bins (banks) results in a high probability of collisions (multiple items per bin).
                        When multiple threads access the same bank (but different addresses), the hardware must serialize the requests, serving them one by one. This serialization penalty is what makes the code slow.
                        While we cannot easily enforce a strict 32-way serialization at every step due to the kernel structure, random strides statistically generate a heavy collision load compared to any conflict-free pattern.
                    \end{answer}

              \item Implement your kernel to perform your access patterns from Q2.a and Q2.b. Report the execution times you measure. From this data, what is the execution time penalty for a warp to perform a shared memory read with maximum collisions.

                    \begin{answer}
                        \textbf{Experiment Parameters:} \\
                        $n = 1024$ \\
                        $threads\_per\_block = 256$ \\
                        $n\_read = 50,000$ \\
                        \\
                        \textbf{Conflict Free (Stride 1):} 2.81 ms \\
                        \textbf{Conflicted (Random):} 4.45 ms
                        \\ \\
                        The execution time penalty is approximately:
                        $$ \frac{4.45}{2.81} \approx 1.58 $$
                        So the random bank conflicts cause roughly a $1.6\times$ slowdown (or 58\% increase in execution time) for this specific kernel configuration and workload.
                    \end{answer}

          \end{enumerate}
