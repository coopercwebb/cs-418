          Calling \code{twiddle} is not a very satisfactory solution.  We never know that we've
          waited long enough, and in most cases, we'll wait longer than needed.  We could use a
          memory fence instead of calling \code{twiddle}, but we know that fences slow all of the
          processors down.  Instead, we'll examine a solution using atomic compare-and-exchange,
          \code{cmpxchg}, instructions.  For example,\\
          \rule{1.5em}{0ex}\code{cmpxchg [\%dst] \%exp \%val}\\
          reads the value at memory location whose address is given by register \code{\%dst}.
          If this value matches the value in register \code{\%exp} (the expected value),
          then the value of register \code{\%val} is written to memory location \code{[\%dst]}.
          If the values don't match, then the memory value is unchanged, but register \code{\%exp}
          is updated to the value in memory.

          The compare-and-exchange operation is performed as an \textit{atomic} operation:
          no other reads or writes of memory location \code{[\$dst]} can take place between
          the read and write.  I'm most familiar with how this was done on a SPARC where the
          caches had a ``read-with-intention-to-write'' operation.  The value at the specified
          address is read, and the cache moves to state \code{M} (or stays in \code{M} if already there).
          Any other caches holding the line for that address move to state \code{I}.
          The cache for the processor performing the compare-and-exchange operation will hold
          on to the line (even if there are pending reads or writes from other processors),
          until the local processor signals that the instruction has completed.
          This makes it essential that the read, compare, and write are done as a single
          instruction -- the CPU cannot be interrupted in the middle of this sequence.

          It is simple to implement a lock using compare-and-exchange.
          We assign a unique, non-zero, \code{int} valued id to each thread.
          The lock is implemented with a shared, \code{int} valued memory location,
          \code{lock->data}.
          \begin{itemize}
              \item When \code{lock->data == 0}, the lock is free.
              \item When \code{lock->data != 0}, \code{lock->data} is the thread-id of
                    the thread holding the lock.
              \item To acquire the lock, a thread spins, reading \code{lock->data}
                    until it reads a value of \code{0}.
                    \begin{itemize}
                        \item The thread then does a compare-and-exchange operation
                              to set \code{lock->data} to its thread-id if \code{lock->data}
                              is still 0.
                        \item If the compare-and-exchange fails, then the thread goes
                              back to spinning until \code{lock->data==0}.
                    \end{itemize}
              \item To release the lock, the thread that owns the lock sets
                    \code{lock->data} to \code{0}.
          \end{itemize}
          Unlike Dekker's algorithm that can only provide mutual-exclusion between two
          threads, the compare-and-exchange lock can provide mutual-exchange between
          an arbitrary number of threads.
          A compare-and-exchange operation can operate on a single ``word'' which can
          be 4 or even 8 bytes.  By using such a word to hold the thread-id of the lock
          owner, we can construct a lock that can handle a *very* large number of threads.

                    \begin{description}
                        \item{\code{\textit{type}}:} the type of the values in the operation.
                        \item{\code{ptr}:}

                        \item{\code{expected}:}

          With that explanation, we can now present our lock;
          see \hrefc{\srcdir/cx.c}{\texttt{cx.c}}.  The acquire function is (with a few assertions elided for clarity):
          \begin{xcode}
              static void cx\_acquire(Lock *lock, int thread\_id) \{\\
              \>int zero;\\
              \>int id1 = thread\_id + 1;\\
              \>int *data = (int *)(lock->data);\\
              \>do \{\\
              \>\>zero = 0;\\
              \>\>while(\_\_atomic\_load\_n(data, \_\_ATOMIC\_SEQ\_CST));\\
              \>\} while (!\_\_atomic\_compare\_exchange\_n(data, \&zero, id1, false, \=\_\_ATOMIC\_SEQ\_CST,\\
              \>                                                                      \>\_\_ATOMIC\_SEQ\_CST));\\
              \}
          \end{xcode}
          And here are some comments:
          \begin{description}
              \item{\code{zero = 0}:} \code{zero} is the value that we want to see in \code{*data} to be able
                    to acquire the lock.  Because \code{zero} is updated by
                    \code{\_\_atomic\_compare\_exchange\_n} when \code{*data != zero}, we restore it for each
                    iteration of the \code{do \{\textrm{~\ldots~}\}} loop.
              \item{\code{while(\_\_atomic\_load\_n(data, \_\_ATOMIC\_SEQ\_CST))}}: spin until the lock is free.
                    The x86 assembly generated by \texttt{gcc -O2 -S cx.c} for this loop is:
                    \begin{xcode}
                        .L2: \=movl\rule{0.5em}{0ex} \=(\%rdx), \%eax\rule{1.5em}{0ex} \={\color{CommentColor}; \%eax <- \code{*data}}\\
                        \>testl                 \>\%eax, \%eax                    \>{\color{CommentColor}; \textrm{set condition flags}}\\
                        \>jne                   \>.L2                             \>{\color{CommentColor}; \textrm{continue if \code{*data != 0}}}
                    \end{xcode}
                    The read of \code{*data} is done with a single instruction, and no special treatment for the memory model.
              \item{\code{\} while (!\_\_atomic\_compare\_exchange\_n(\textrm{\ldots}))}:}
                    The atomic compare-and-exchange.  If it fails, we go back to spinning until \code{*data == 0}.
                    If it succeeds, we've acquired the lock and continue.
                    The x86 assembly generated by \texttt{gcc -O2 -S cx.c} for this is:
                    \begin{xcode}
                        \phantom{.L2:} \=lock \=cmpxchgl \=\%esi, (\%rdx)\\
                        \>jne      \=.L2\\
                        \>ret

                    \end{xcode}
                    Looking back a few lines in the assembly code (you can give the command \texttt{gcc -O2 -S cx.c}),
                    we can determine that \code{\$esi} is \code{id1} and \code{\%drx} is \code{data}.
                    Register \code{\%eax} is \emph{always} used for the expected value -- this is x86 assembly code;
                    I don't explain its odd quirks.
                    \par
                    An optimization that I noted is that there is no register for \code{zero}.
                    That's when the\\
                    \rule{1.5em}{0ex}\code{while(\_\_atomic\_load\_n(data, \_\_ATOMIC\_SEQ\_CST));}\\
                    loop terminates, the value from the load, which is in register \code{\%eax} must be \code{0}.
                    The compiler uses this \code{0} for \code{expected}.
                    Executing \code{cmpxchgl} sets the x86 condition flags.
                    If the value of \code{*data} not \code{0}, the \code{jne} goes back to the \code{while}-loop.
                    Otherwise, the lock is successfully acquired, and the function returns.
          \end{description}
          Releasing a lock is much simpler: just store \code{0} at \code{lock->data}.

          And finally, \ldots {\large\textbf{More questions!}}
          \begin{enumerate}\setcounter{enumii}{2}
              \item (15 points) Consider an execution with $N$ threads numbered $1$ through $N$.
                    Assume that thread $1$ holds the lock, and that the other threads are spinning.
                    In this situation, threads $2$ through $N$ hold the cache line for \code{lock->data} in the \code{S} state.
                    For simplicity, assume that thread $1$ holds this cache line in the \code{S} state as well.
                    Describe the memory accesses that are performed and the cache-line state transitions
                    (e.g.\ from \code{S} to \code{I} or vice-versa) when thread 1 releases the lock,
                    one of the other threads acquires the lock, and the other threads resume spinning.

                    \begin{answer}
                        \textbf{Phase 1: Thread 1 releases the lock}

                        Thread 1 executes \code{\_\_atomic\_store\_n(data, 0)} to release:
                        \begin{itemize}
                            \item Thread 1 cache: $S \to M$ (needs exclusive access to write)
                            \item Thread 1 sends BusInv to all other caches
                            \item Threads 2-N caches: $S \to I$ (invalidated)
                            \item Thread 1 writes 0 to cache line, propagates to memory
                        \end{itemize}

                        \textbf{Phase 2: Spinning threads detect lock is free}

                        Threads 2-N are spinning in \code{while(\_\_atomic\_load\_n(data))}:
                        \begin{itemize}
                            \item All N-1 threads have cache line in $I$ state, must fetch from memory
                            \item All issue memory reads (approximately) simultaneously
                            \item Thread 1 cache: $M \to S$ (or $E$, responds to reads)
                            \item Threads 2-N caches: $I \to S$ (all read value 0)
                        \end{itemize}
                        This requires O(N) memory reads.

                        \textbf{Phase 3: One thread acquires the lock}

                        All N-1 threads see lock is free and attempt \code{cmpxchgl}. Say thread 2 wins arbitration:
                        \begin{itemize}
                            \item Thread 2 executes \code{cmpxchgl} (read-with-intent-to-write)
                            \item Thread 2 cache: $S \to L$ (locked during atomic operation)
                            \item Thread 2 sends BusInv to all other caches
                            \item Thread 1, threads 3-N caches: $S \to I$ (invalidated)
                            \item Thread 2 compares (expected=0, actual=0), writes thread\_2\_id
                            \item Thread 2 cache: $L \to M$
                            \item \code{cmpxchgl} succeeds
                        \end{itemize}

                        \textbf{Phase 4: Other threads fail to acquire and resume spinning}

                        Each of threads 3-N attempts \code{cmpxchgl}:
                        \begin{itemize}
                            \item Thread $k$ (for $k \in \{3,...,N\}$) executes \code{cmpxchgl}
                            \item Thread $k$ cache: $I \to L$ (locked during read-with-intent-to-write)
                            \item Thread $k$ must wait for thread 2's cache to finish (bus arbitration)
                            \item Thread $k$ reads value (thread\_2\_id), compares with expected (0), fails
                            \item Thread $k$ cache: $L \to E$ or $M$ (has exclusive copy momentarily)
                            \item Each failed \code{cmpxchgl} sends BusInv, invalidating other spinning threads
                            \item Thread $k$ returns to \code{while} loop, reads lock value again
                            \item Thread $k$ cache: likely $I$ again after other threads' \code{cmpxchgl} attempts
                        \end{itemize}

                        After all failed attempts, threads resume spinning:
                        \begin{itemize}
                            \item Thread 2 cache: $M$ (holds lock)
                            \item Threads 3-N must read from thread 2's cache or memory
                            \item Threads 3-N caches: $I \to S$ (read non-zero value)
                            \item Thread 2 cache: $M \to S$ (shared with spinning threads)
                        \end{itemize}

                        \textbf{Big-O Analysis:}

                        The compare-and-exchange lock generates $\Theta(N^2)$ inter-cache and memory activity:
                        \begin{itemize}
                            \item Release: O(N) invalidations
                            \item All threads read lock is free: O(N) memory reads
                            \item Each of N-1 threads attempts \code{cmpxchgl}: each attempt causes O(N) invalidations
                            \item Total: $O(N) + O(N) + O(N) \cdot O(N) = O(N^2)$ cache coherence traffic
                        \end{itemize}

                        This excessive traffic is why more sophisticated locking algorithms (e.g., queue-based locks, MCS locks) are preferred for high-contention scenarios.
                    \end{answer}

          Hints: there are many details I could add about exactly how a cache handles read-with-intent to write, and so on.
          Here are some assumptions that I'll suggest to keep the problem simple:
          \begin{itemize}
              \item When a processor does a ``read-with-intent-to-write'',
                    if the cache line is in the \code{I} or \code{S} states, the value is read from memory, \textit{and}
                    the other caches are signaled with \emph{BusInv} to invalidate their entries
                    for that line.
                    If the cache line for the address is already in states \code{E} or \code{M}, no action with external memory
                    is needed.
                    In either case, cache moves to a new state, \code{L}.
                    When the processor writes to the address, the cache-line moves to state \code{M}.
                    If the compare part of the compare-and-swap fails,
                    then the processor signals to the cache to move to state
                    \code{M}.\footnote{
                        Note: the cache moves to state \code{M} because it could have entered state
                        \code{L} from any of the other states, i.e.\ \code{M}, \code{E}, \code{S}, or
                        \code{I}.  If the cache was in state \code{M} when the read-with-intent-to-write
                        operation starts, it must move to state \code{L} to prevent any state transitions
                        until the read-with-intent to write operation finishes.
                        Because he cache may have entered state \code{L} from state \code{M}, then
                        we can't assume that main memory has the up-to-date value for the location.
                        Thus, the cache moves to state \code{L} when leaving state \code{M}.
                        \par
                        Of course, cache designers can make variations on this.  We could have two
                        version of the \code{L} state to indicate whether or not the cache line is dirty.
                        Or, we could always do a write back at the end of the read-with-intent-to-write,
                        just writing the value we read if the compare-and-exchange fails.
                        I'm sure there are many other variations, and they've probably all been
                        studied by those who have dedicated their careers to cache design.}
                    While the cache is in state \code{L}, it signals a stall to any other cache that requests the cache line
                    through a memory read or write.  The operation is delayed until the cache line moves to state \code{M} or \code{E},
                    and then the operation is handled according to the usual MESI protocol.
                    There are many ways we could optimize this protocol, but I want to keep it simple.
              \item When threads $2$ through $N$ are spinning, you can assume that they all attempt to load from
                    \code{lock->data} on the same clock cycle.  If the loads hit in their caches, then they all get the
                    data locally; otherwise, each cache misses and they each issue a memory read.
              \item When the thread for a cache starts a \code{cmpxchgl} instruction, all other caches invalidate their
                    lines for \code{lock->data}.  If multiple threads attempt a \code{cmpxchgl} at the same time,
                    there is memory-bus arbitration in the hardware that makes the threads do these operations one at a time.
          \end{itemize}
          Hint: you should find that a compare-and-exchange lock generates a lot of inter-cache and memory activity
          when multiple threads are spinning and waiting for the lock.  Give a big-$\bigO$ characterization of how
          much memory and inter-cache activity occurs.  There are better algorithms for locking.  By working this
          example, you should get a good sense of how protocols like MESI work in real life.

          Finally, a word about weak consistency.  Instructions such as \code{cmpxchgl} ensure that the write is
          completed in main memory before the instruction completes.  This makes the write visible to all other
          processors.  This also means that all previous writes by that processor will have propagated to main
          memory.  It makes no guarantee about pending writes from other processors.

          For this problem, we will use dimension routing, where messages are first routed according
          to the least significant bit of their destination.

          We want an example that causes severe congestion in the hypercube.
          To define congestion we will first define a ``traffic pattern''.
          A traffic pattern is a list of \code{\tuple{Src, Dst}} tuples, where
          \code{Src} and \code{Dst} are node addresses.
          For each element of the list, a message is to be sent from the \code{Src}
          node \code{Dst}.  We will say that a traffic pattern is crossbar-routable
          in one step if there are no two tuples with the same \code{Src} node,
          and there are no two tuples with the same \code{Dst} node.

          A traffic pattern that is crossbar-routable in one step may cause congestion
          on a hypercube using dimension routing.
          For example, on a 4-dimensional traffic pattern the traffic pattern:
          \begin{xcode}
              [\tuple{[0,1,0,1], [1,0,0,1]}, \tuple{[1,1,0,1], [1,0,0,0]}]

          dimension routing when both messages need to use the dimension-1 link from node \code{[1,1,0,1]}
          to node \code{[1,0,0,1]}.

                    \begin{answer}
                        \textbf{Proof:}

                        Consider the transpose traffic pattern on a $D$-dimensional hypercube where $D$ is even.
                        Each node with address $\code{Addr} = \code{Left} ++ \code{Right}$ (where $|\code{Left}| = |\code{Right}| = D/2$)
                        sends a message to its transpose $\code{Right} ++ \code{Left}$.

                        \textbf{Key Observation:} Consider the link from node $[0,0,\ldots,0]$ (all zeros) along dimension $D/2$.

                        \textbf{Which messages use this link?}

                        A message from $\code{Src}$ to $\code{Dst}$ uses this link if and only if:
                        \begin{enumerate}
                            \item After routing along dimensions $0$ through $D/2-1$, the message reaches node $[0,0,\ldots,0]$
                            \item The message needs to change bit $D/2$ (i.e., $\code{Src}[D/2] \neq \code{Dst}[D/2]$)
                        \end{enumerate}

                        \textbf{Pattern of sources:}

                        For the transpose pattern, consider sources of the form:
                        $$\code{Src} = [1, b_1, b_2, \ldots, b_{D/2-1}, 0, 0, \ldots, 0]$$
                        where the first $D/2$ bits can vary (with first bit fixed to 1), and the last $D/2$ bits are all 0.

                        The destination is:
                        $$\code{Dst} = [0, 0, \ldots, 0, 1, b_1, b_2, \ldots, b_{D/2-1}]$$

                        \textbf{Routing analysis:}
                        \begin{itemize}
                            \item Dimensions 0 through $D/2-1$: The message routes from $\code{Src}$ to match the first $D/2$ bits of $\code{Dst}$,
                                  arriving at node $[0,0,\ldots,0,0,\ldots,0]$.
                            \item Dimension $D/2$: The message must change from 0 to 1, using the link from $[0,0,\ldots,0]$ along dimension $D/2$.
                        \end{itemize}

                        \textbf{Counting messages:}

                        How many such source nodes exist? The pattern $[1, b_1, \ldots, b_{D/2-1}, 0, \ldots, 0]$ has:
                        \begin{itemize}
                            \item First bit: fixed to 1 (to ensure dimension $D/2$ link is used)
                            \item Next $D/2-1$ bits: can be anything ($2^{D/2-1}$ choices)
                            \item Last $D/2$ bits: all 0
                        \end{itemize}

                        Total messages using this link: $2^{D/2-1} = \frac{1}{2} \cdot 2^{D/2}$.

                        \textbf{Conclusion:} The link from node $[0,0,\ldots,0]$ along dimension $D/2$ conveys exactly

    \item Work-Span and Dynamic Programming: \textbf{(30 points)}\\
          Dynamic programming is a method for solving optimization problems when we have a way of breaking the
          problem into smaller problems, we can define an ordering of the sub-problems, and it's ``easy'' to
          solve a sub-problem once all of the sub-problems that are earlier in the ordering have been solved.
          A classical example is the editing distance between two strings: if we have two strings, $s_1$ and $s_2$,
          and have a costs associated with inserting a character, $c_{\mathit{ins}}$,
          a cost for deleting a character, $c_{\mathit{del}}$, and
          a cost for replacing a character with another one, $c_{\mathit{rpl}}$,
          what is the minimum cost sequence of operations that transforms string $s_1$ into string $s_2$?
          See, for example,\\
          \rule{1.5em}{0ex}\textit{\hrefc{https://doi.org/10.1016/0022-2836(70)90057-4}{A general method applicable to the search for similarities in the amino acid sequence of two proteins}},\\
          S.B.\ Needleman \& C.D.\ Wunsch.

          Let's say that $s_1$ has $n$ characters and $s_2$ has $m$ characters.
          We can solve the editing distance problem by filling in a $(n+1) \times (m+1)$ tableau, $T$.
          Initialize $T(0, 0:m)$ and $T(0:n, 0)$ with
          \begin{displaymath}\begin{array}{rcl}
                  T(0, j) = j*c_{ins} \\
                  T(i, 0) = i*c_{del}
              \end{array}\end{displaymath}
          For each $(i,j)$ with $0 < i < n$ and $0 < j < m$,
          if we have filled in $T(i-1, j-1)$, $T(i-1, j)$, and $T(i, j-1)$, the we can set $T(i,j)$ according to:
          \begin{displaymath}
              \begin{array}{rcl}
                  T(i,j) & = & \left\{\begin{array}{ll}
                                          \min(T(i-1, j-1), T(i-1, j) + c_{del}, T(i,j-1) + c_{ins}),           & \textrm{if $s_1(i) = s_2(j)$}    \\
                                          \min(T(i-1, j-1) + c_{rpl}, T(i-1, j) + c_{del}, T(i,j-1) + c_{ins}), & \textrm{if $s_1(i) \neq s_2(j)$}
                                      \end{array}\right.
              \end{array}
          \end{displaymath}
          In English, this means:
          \begin{itemize}
              \item If we have already matched the first $i-1$ characters of $s_1$ to the first $j-1$ characters of $s_2$
                    with a cost of $T(i-1, j-1)$, then
                    \begin{itemize}
                        \item if the $i^{th}$ character of $s_1$ matches the $j^{th}$ character of $s_2$,
                              then we can match the first $i$ characters of $s_1$ to the first $j$ characters of $s_2$ with a cost
                              of $T(i-1, j-1)$.  In other words, there is no cost if the corresponding character match.
                        \item otherwise,
                              we can match the first $i$ characters of $s_1$ to the first $j$ characters of $s_2$ with a cost
                              of $T(i-1, j-1) + c_{\mathit{rpl}}$.  In other words, we replace the $i^{th}$ character of $s_1$ with the
                              $j^{th}$ character of $s_2$.
                    \end{itemize}
              \item If we have already matched the first $i-1$ characters of $s_1$ to the first $j$ characters of $s_2$
                    with a cost of $T(i-1, j)$,
                    then we can match the first $i$ characters of $s_1$ to the first $j$ characters of $s_2$
                    with a cost of $T(i-1, j) + c_{\mathit{del}}$, by deleting the $i^{th}$ character of $s_1$.
              \item If we have already matched the first $i$ characters of $s_1$ to the first $j-1$ characters of $s_2$
                    with a cost of $T(i, j-1)$,
                    then we can match the first $i$ characters of $s_1$ to the first $j$ characters of $s_2$
                    with a cost of $T(i, j-1) + c_{\mathit{ins}}$, by inserting the $j^{th}$ character of $s_2$ into $s_1$.
          \end{itemize}
          We choose the cheapest of these options for the cost of $T(i, j)$.
          Note that there is never an advantage of choosing a more expensive solution for $T(i, j)$ when finding
          solutions that are later in the tableau.
          \par

                        $E(n) = S(n, p_{\max}(n))/p_{\max}(n) = (n/2)/n = 1/2 = 50\%$. Therefore, $\lim_{n \to \infty} E(n) = 1/2$. The efficiency is less than one due to \textbf{load imbalance}: not all diagonals have $n$ cells. Diagonals near the corners have few cells, leaving many processors idle. Only the middle diagonals fully utilize all $n$ processors.
                    \end{answer}
          \end{enumerate}
\end{enumerate}
